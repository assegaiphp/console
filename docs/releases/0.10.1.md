# Assegai Console 0.10.1

Assegai Console 0.10.1 makes CLI and application upgrades explicit, reviewable, and recoverable.

## CLI self-updates

Console can now update its global installation without asking users to manage Composer's global requirement directly:

```bash
assegai global update
# shorthand
assegai -g update
```

The command checks the latest stable Console release and runs the necessary global Composer transaction with all dependent packages. `--dry-run` previews that transaction. If the version service is temporarily unavailable, Composer resolves the latest release directly instead of leaving the user without an upgrade path.

Every normal CLI command also performs a cached, short-timeout release check. New-version notices go to stderr and include both self-update forms; network or metadata failures remain silent and never block the requested command.

This capability begins in 0.10.1. An already-installed 0.9 binary cannot gain a command that it does not contain, so a no-manual-step 0.9-to-0.10 rollout still requires an updater-enabled bridge build or managed installer to be distributed before the migration is announced as fully self-service.

## Upgrade sequence

Once an updater-enabled Console is installed, update the global CLI first, preview the workspace migration, and then approve it:

```bash
assegai global update
assegai update --to=0.10 --dry-run
assegai update --to=0.10
```

Automated environments can use `--yes` after reviewing the dry-run output. Without that flag, a non-interactive cross-release update stops before changing the workspace.

## Deliberate package alignment

The update plan shows direct requirement changes before Composer runs. Core, ORM, and the coordinated first-party packages move to `^0.10.0`. A project-local `assegaiphp/console` requirement also moves in the same transaction, avoiding the Common 0.9/0.10 conflict caused by trying to upgrade a local CLI independently.

Events participates in the coordinated 0.10 release line. Queue drivers keep their independently published 1.x compatibility constraints while still participating in Composer resolution when directly installed.

## Recovery boundary

Before mutation, the CLI snapshots `assegai.json`, `composer.json`, and `composer.lock`. If configuration migration or Composer resolution fails, those manifests are restored. Because Composer scripts may have touched `vendor/` before failing, the CLI tells the user to run `composer install` when dependency state needs to be reconciled with the restored lock file.

The update command does not rewrite application PHP source or create `config/auth.php`. Authentication redirect policy and legacy session settings require an application-specific review; keeping that step manual prevents a default auth scaffold from overriding customized 0.9 session configuration.

## Validation

Regression coverage verifies dry-run immutability, explicit non-interactive approval, project-local Console alignment, mismatched target rejection, and manifest restoration after Composer failure.
