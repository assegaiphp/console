# Assegai Console 0.11.1

Console's package catalog, new-project defaults and update planner now use one reviewed, offline framework inventory. This corrects the mixed 0.10/0.11 recommendations shipped in Console 0.11.0.

The coordinated minimums are Core, Console and Starter `0.11.1`; supporting framework modules `0.11.0`; RabbitMQ and Beanstalkd `1.2.0`; and the established Attributes dependency `1.0.3`. Module release versions follow those coordinated streams. Consumer requirements can retain reviewed older support alongside acceptance of the coordinated targets. Unreleased modules remain accounted for without becoming public installation recommendations.

`assegai add rabbitmq` now selects `~1.2.0`. Unrestricted first-party wildcard recommendations and the installed-alias bypass for unreviewed first-party modules have been removed. A package absent from the public inventory produces an explanation and CLI self-update instructions.

`assegai update --to=0.11 --dry-run` previews the coordinated requirement changes, including installed queue adapters and `require-dev` dependencies. Cross-release changes still require confirmation or an explicit `--yes`. Existing compatible requirements and support unions are preserved. Support removals are previewed and require explicit approval, including minimum-runtime changes within the same framework line. Unsupported newer upgrades, development branches, unbounded first-party requirements and custom ranges that cannot be changed safely block before any project files or dependencies are changed. Failed Composer operations retain the existing manifest rollback behavior.

New projects receive Core `~0.11.1` from the same inventory. The Composer template no longer carries a separately maintained Core version.

Console accepts Common `^0.10.1 || ~0.11.0`, preserving its published queue contract while admitting the coordinated target. The shipping lock retains the published Common artifact until an actual dependency update is qualified.

The read-only `release:check` command and standalone package-policy entrypoint validate canonical membership, mapped streams, minimums and source-bound evidence. Structural package checks, verified consumer support and full release readiness have distinct purposes and evidence scopes. Prepare and Publish checks remain separate; extra support requires source-bound reviewed intervals and separately recorded executed graph samples. Publish also checks the actual Website Composer files, so documentation rendered on an old dependency graph cannot qualify the target release. See [Coordinated release checks](../release-checks.md).

The internal update-guide scaffolder no longer guesses Website/Core paths or writes directly into their catalogs. It requires an explicit draft output directory outside source repositories and Composer projects, refuses existing targets, and leaves admission to the Website owner.
